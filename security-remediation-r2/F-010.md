# F-010 — Competition Import resource amplification remediation

Date: 2026-08-31

Baseline: `75338bcd2d4ca6b53f146626bce66b9923714506`

Status: **FIXED**

## Confirmed pre-remediation order

The original path was re-read before implementation:

`HTTP request -> optional numeric Content-Length preflight -> request.formData() -> File -> arrayBuffer()/UTF-8 text -> CSV/XLSX materialization -> logical validation`

Consequences confirmed by accepted R2 evidence were a 4,894,904-byte valid CSV causing `+188,035,072` bytes RSS and a chunked/no-length request reaching multipart buffering. The current `read-excel-file` public API exposes workbook materialization, not a safe central-directory metadata preflight. Its internal ZIP package is transitive and was not imported as an undeclared product dependency.

## Implementation

### Multipart boundary

The competition-import request reader now requires a present, decimal, positive, safe-integer `Content-Length` before `request.formData()`:

- missing: HTTP 411;
- syntactically invalid, zero, negative, or unsafe: HTTP 400;
- above the existing 5 MiB file limit plus 256 KiB multipart envelope: HTTP 413.

The existing content-type, decoded `File.size`, extension, UTF-8, authorization, Origin, preview, and commit rules remain in place. The deterministic test uses a `formData()` trap and proves all header failures happen before multipart materialization. A real Node/browser-compatible `fetch(FormData)` HTTP regression is also a mandatory compatibility gate.

### CSV memory

The CSV/TSV/Paste parser now scans once and emits normalized import rows incrementally. It no longer builds a complete `string[][]` and then a second mapped row structure, and it no longer appends every character to a growing JavaScript string. Quoted fields, escaped quotes, embedded newlines, BOM, row numbers, unknown-header warnings, and headerless team Paste remain compatible.

New parser resource contracts:

- 5,000 business rows (existing limit);
- 32 columns per row;
- 2,048 characters per cell.

The complete input is still bounded by the existing 5 MiB upload contract, but the duplicate whole-file row materialization was removed without changing the downstream normalized-row interface.

### XLSX preflight

`src/lib/competition-import-xlsx-security.ts` implements a deliberately limited OOXML ZIP preflight, not a general ZIP extraction library. It reads EOCD/central-directory and local-entry metadata, rejects unsupported multi-disk, ZIP64, encrypted, duplicate, unsafe-path, or unsupported-compression structures, and uses Node's built-in bounded `inflateRawSync(maxOutputLength)` for only the XML entries that `read-excel-file` would read after metadata budgets pass. This validates actual size against declared size and closes under-declared shared-string/style/workbook XML bypasses. Only worksheet XML is decoded/scanned for dimensions and cells; entries are handled sequentially and not retained. The existing `read-excel-file` parser runs only after this preflight.

No new dependency or dependency upgrade was introduced.

| Limit | Value | Rationale | Normal fixture / headroom |
|---|---:|---|---|
| compressed XLSX | 5 MiB | Existing product upload contract, now also asserted at preflight API | 1,574 bytes in HTTP fixture |
| ZIP entries | 128 | Far above ordinary OOXML package needs while bounding metadata work | 5 entries; 25.6x entry headroom |
| total uncompressed bytes | 16 MiB | More than 3x compressed business ceiling, but blocks the accepted 455.89x expansion | deterministic normal: 1,783 bytes |
| worksheet XML entry | 8 MiB | Bounds the largest parser-facing XML allocation below total budget | normal worksheet is under 1 KiB |
| per-entry and total compression ratio | 120:1 | Ample above normal fixture `1.8:1`, below accepted malicious `455.89:1` | 66.7x ratio headroom |
| worksheets | 8 | Product imports only the first sheet, so more is unnecessary parser work | 1 sheet; 8x headroom |
| rows / columns | 5,001 including header / 32 | Preserves 5,000 business rows and bounds sparse dimensions | normal 2 x 2 |
| total worksheet cells | 160,032 | Exact maximum implied by 5,001 x 32; blocks duplicate/sparse cell amplification | normal 4 cells |

## Deterministic regressions

`npm.cmd run test:security-runtime-r2` passed on Node `v22.23.2`.

- normal CSV, quoted CSV, Paste, and exact 5,000-row input: PASS;
- 5,001 rows, 33 columns, and 2,049-character cell: HTTP/parser 413 contract PASS;
- normal project-specific XLSX: full preflight and parser PASS;
- compressed file bytes, high ratio, declared total uncompressed bytes, worksheet XML bytes, 129 entries, row 5,002, column 33, and cell 160,033: pre-parser HTTP/parser 413 contract PASS;
- under-declared parser-relevant XML actual-size mismatch: pre-parser 415 PASS;
- missing, invalid, zero, and above-envelope `Content-Length`: rejected before `formData()` PASS.

Declared uncompressed/XML overflow fixtures modify central-directory size metadata on a tiny archive so rejection is proven without allocating the declared expansion. The cell-count fixture is stored (ZIP level 0), under 2 MiB, and the high-ratio fixture expands only about 512 KiB. No fixture exceeds the accepted R2 payload scale.

## Production-mode resource before/after

Environment: Node `v22.23.2`, built production `next start`, localhost, disposable SQLite/account/competition, fresh server per case, 10 ms process metrics, 512 MiB RSS safety stop. Seven bounded cases were run. Preview left Team/Match/AuditLog counts at `0/0/0`.

For the identical 4,894,904-byte valid CSV:

- accepted R2 before: `+188,035,072` RSS (`179.32 MiB`), `359.796 ms`;
- remediation after: `+39,542,784` RSS (`37.71 MiB`), `66.912 ms`;
- reduction: `148,492,288` bytes, or `78.97%`.

The comparison gate required at least a 50% reduction relative to the accepted R2 baseline; it passed. This is a comparative regression gate, not an arbitrary universal process-memory promise.

The high-ratio XLSX was rejected by the new central-directory compression-ratio check before worksheet inflation and before `read-excel-file`. The chunked request returned 411 with only 495,616 bytes observed RSS increase in the request window and never reached multipart parsing. No safety stop fired.
